# Go port

The backend moves from TypeScript (TanStack Start server, Node runtime, `packages/core`, `packages/connectors`, `packages/db`) to one Go binary. The React dashboard stays and becomes a static single-page app that the binary serves. The goal is a small image (about 50 MB instead of 399 MB) and lower memory.

This file is the working plan. Each milestone is done by one agent with no memory of the others, so everything a later agent needs is written here. Update the Status table and the Decisions log as you go.

## Rules for every milestone

1. The TypeScript source is the spec. Port behavior exactly: status values, limits, timeouts, backoff ladders, error text, and every bot-facing string (casual Indonesian, copied verbatim). When the TS code and `docs/PLAN.md` disagree, the code wins. Do not redesign.
2. Port the tests too. Every `foo.test.ts` in the area you port gets a Go test that covers the same cases. Functions keep an explicit clock (`now` as a parameter or an injected clock), the way the TS code does.
3. Do not delete or edit TypeScript backend code before M10. Until then both stacks live side by side and the TS one keeps running in production.
4. No commits, no stash, no push, no PRs, no posting anywhere. Leave the work in the working tree. Pushing to `main` deploys to production.
5. Never touch the running production stack: compose project `palui`, containers `palui-app-1` and `palui-runtime-1`, volume `palui_data`, port 4802. Scratch containers use another project name, another image tag (`palui-go:dev`) and a free port from 4895 up.
6. One heavy process at a time (install, build, test run, docker build). Check disk and memory first, as the global instructions say. Never start a dev server in the background.
7. Never type a tool or dependency version from memory. Use `go version` for the `go` directive, `go get <module>@latest` for dependencies, and check that a Docker tag exists before using it.
8. The Bash hook blocks any command that contains the text `.env` or reads environment variables (`go env X` is blocked too). Write such files with the Write or Edit tool.
9. English only in code, comments and docs. No em dashes anywhere.
10. Finish only when the gate for your milestone passes. If something cannot be finished, say exactly what and why in the Status table. Never mark a milestone done with failing or skipped tests.

## Target architecture

```
apps/server/                 Go module (go.mod here)
  cmd/palui/                 one binary: `palui serve` plus the admin commands
  internal/config            environment config
  internal/logx              JSON-lines logger with secret redaction
  internal/db                open, pragmas, embedded migrations, schema state
  internal/secret            AES-256-GCM, ids, tokens, masking
  internal/<domain>          one package per packages/core module (chat, flows, reminders, ...)
  internal/connectors/<type> one package per connector
  internal/httpapi           HTTP server: auth, RPC endpoints, SSE, hooks, static dashboard
  internal/web               embedded dashboard build (copied in at build time)
  testdata/                  golden files exported from the TS code
apps/app/                    dashboard: Vite + TanStack Router SPA, no server code
apps/host-bridge, apps/site, apps/edge   unchanged, stay TypeScript
```

Decisions that are already made:

- **One process.** `palui serve` runs the HTTP server, the connector supervisor, the turn engine, the schedulers and the outbox worker together. The app to runtime control API, its token and the SSE proxy go away and become in-process calls. Compose ends up with one service. Each connector and each background loop recovers its own panics so one bad library cannot take the dashboard down.
- **Same database file, same data.** The Go binary opens the existing `$DATA_DIR/palui.db` in place. No data migration. See Compatibility.
- **SQLite driver: `modernc.org/sqlite`** (pure Go, no cgo, so the binary is static). Plain `database/sql` with handwritten SQL, no ORM. Always name columns (the live column order differs from `schema.ts`).
- **Write discipline.** The TS code relies on synchronous SQLite calls so claims never interleave. In Go use one write connection (a pool capped at one) plus a read pool, and keep every claim a single `UPDATE ... RETURNING` statement.
- **Models: own client code, no SDK port.** Two streaming clients behind one interface: Anthropic Messages (`/v1/messages`) and OpenAI-compatible chat completions (`/v1/chat/completions`), both with a configurable base URL. Before writing the Anthropic client, load the `claude-api` skill. Keep the model ids that are in the TS settings defaults.
- **WhatsApp: `go.mau.fi/whatsmeow`.** Its session store is a SQL store with its own tables, kept in a separate file under `$DATA_DIR/wa/<connectorId>.db`, not in `palui.db`. The Baileys session cannot be reused, so the owner pairs WhatsApp again at cutover.
- **Telegram:** long polling against the Bot API. A small in-house client is fine (about eight methods are used).
- **MCP:** the official Go SDK (`github.com/modelcontextprotocol/go-sdk`), Streamable HTTP client only, with a custom HTTP client for the public-address guard.
- **Recurrence and time:** `github.com/teambition/rrule-go` plus the standard `time` package with `time/tzdata` embedded. Wall-clock rules keep the TS semantics (DST gap shifts forward, overlap takes the earlier instant).
- **Auth: no Better Auth.** Go owns sessions and passkeys (`github.com/go-webauthn/webauthn`) on the existing `user`, `session`, `account` and `passkey` tables. The owner invite flow keeps its rules (single use, 15 minutes, recovery wipes sessions and passkeys) but signs the owner in directly instead of through a generated password.
- **Dashboard API.** Each of the 78 server functions becomes `GET` or `POST /api/rpc/<functionName>` with the same input and output JSON. On the dashboard side the files in `apps/app/src/lib/fns` keep their names and exported functions and become thin `fetch` wrappers, so call sites do not change. Every endpoint keeps its guard: session required (except the three public ones), same-origin check on every write.
- **Manifests.** Go defines the connector manifests natively. The dashboard keeps its TS manifests for the forms. A golden file exported from TS keeps the two in parity (ids, kinds, flags, field and secret names, setup steps).

## Compatibility contracts

These must match the TS build byte for byte, and each has a golden test.

- **Migrations.** Tracking table `_migrations(name TEXT PRIMARY KEY, applied_at INTEGER NOT NULL)`, `applied_at` in Unix ms. A migration is applied when its name (file basename without `.sql`) is in the table. Statements are split on `--> statement-breakpoint` and each migration runs in one transaction. Copy the 16 files from `packages/db/drizzle/*.sql` into the Go module with the same names. A test keeps them identical to the TS copies while those exist. New migrations after the port are handwritten SQL.
- **Schema state.** `ok`, `behind` (bundled names missing from the table) or `newer` (unknown names in the table). `/health` returns 503 `db_newer_than_app` only for `newer`.
- **Pragmas on every connection:** `journal_mode = WAL`, `synchronous = NORMAL`, `foreign_keys = ON`, `busy_timeout = 5000`.
- **Timestamps** are integer Unix ms. JSON columns are text. Booleans are 0 or 1.
- **Secrets** (`packages/db/src/crypto.ts`). Key is `SHA-256("palui:secrets:v1:" + MASTER_KEY)`, the key string used as is. AES-256-GCM, 12-byte IV, 16-byte tag, no AAD. Text form `v1.<iv>.<tag>.<ct>`, each part base64url without padding (in Go: `gcm.Open(nil, iv, ct||tag, nil)`). Binary form for `saved_attachments.data`: `iv[0:12] | tag[12:28] | ct[28:]`. Encrypted columns: `connectors.secrets` (JSON object of strings), `hooks.secret`, `saved_attachments.data`. The dev fallback key and the 32-character minimum stay.
- **Ids** (`packages/db/src/ids.ts`). `<prefix>_<9 chars base36 ms time><10 chars base36 random>`, monotonic inside one process. Keep every prefix.
- **Stored JSON shapes.** `messages.content`, `pending_approvals.messages` and `pending_approvals.context` hold AI SDK v7 message JSON written by the TS build. The Go message types must read and write that shape, because history replay reads old rows. Flow definitions, flow run state, outbox payloads and settings values keep their shapes too.
- **Hook signatures.** HMAC-SHA256 over `<timestamp>.` plus the raw body, hex, `sha256=` prefix, computed before any parsing.
- **Outbox action ids** stay as listed in `AGENTS.md` (`approve:<id>`, `rem:snooze:<id>:<10m|1h|tomorrow>`, `fl:<runId>:<answerId>` and the rest).
- **Tool names** stay `<connectorId>__<tool>`, sanitized and capped at 64 characters. Tool names, descriptions, classes and input JSON schemas must match the TS build (golden file), because they shape model behavior and the prompt cache.
- **Lengths.** The TS limits count UTF-16 code units. Match them where a limit is user-visible or stored.

Things that are allowed to change at cutover: session cookies (the owner signs in again), in-flight approvals (they expire after 10 minutes, treat unreadable ones as expired), the WhatsApp session (pair again), and the control API (gone).

## Golden files

`apps/server/testdata/gen/` holds TS scripts (run with `pnpm tsx`) that export goldens from the real TS code into `apps/server/testdata/`. They are committed, so they stay as the frozen spec after the TS backend is deleted in M10. M1 creates the first set. Later milestones add theirs:

- crypto vectors, ids, masking, tokens (M1)
- a TS-seeded database: the `worst` fixture plus connectors and a hook with encrypted secrets (M1)
- time and recurrence cases (M2)
- system prompt blocks and message history shapes for fixed inputs, command replies, reports and scripted engine runs (M3, `testdata/chat.json`)
- flow definitions, expression results and run traces (M5)
- every connector's manifest and tool catalog: name, description, class, JSON schema (M6, M7)
- every server function's input and output JSON on the `worst` fixture (M8)

## Cutover (the owner does this, not an agent)

Before merging:

1. Check the Mac mini has room: `df -h /System/Volumes/Data` (deploy.sh refuses under 5 GB; the first Go build pulls `golang` and `alpine` images once).
2. Note the last TypeScript commit on `main` (`2c89fa5` when the port was finished, or whatever `main` is at merge time) for the rollback below.
3. Make sure `~/selfhost/palui/.env` has `MASTER_KEY` and `APP_URL=https://palui.zakiego.com`. A host name, not an IP: with an IP the server starts but turns passkeys off.

Deploy:

1. Merge and let the deploy run. `pre-deploy.sh` snapshots the database first (through the old image's `palui backup`), then stops and removes the old `palui-runtime-1` container: the new compose file has no `runtime` service, so `compose up` would otherwise leave the Node runtime running next to the Go server (two turn engines, two WhatsApp and Telegram sessions on one database). From then until the new container is healthy (the image build, a few minutes on the first deploy) only the old app runs: the dashboard answers but no channel message is handled. Telegram keeps the updates; WhatsApp is paired again anyway.
2. Check `curl -s https://palui.zakiego.com/health`: 200, `version` is the merged version, `runtime` is an object with `ok: true` (not `"unreachable"`). `docker ps -a --filter label=com.docker.compose.project=palui` lists only `palui-app-1`, and `docker image ls palui` shows `latest` at about 42 MB.
3. Sign in to the dashboard again (every old session ended). The old passkey should work; if it's refused, run `docker compose exec app palui owner invite` and enroll a new one.
4. Pair WhatsApp again from its connector page (the Baileys session isn't read).
5. Send one message on each channel (web chat, Telegram, WhatsApp) and check the reply. Open Activity and check a reminder or job still fires on time.
6. Run the restore drill once against the new image: `scripts/restore-drill.sh` (it needs the production `MASTER_KEY` in its environment and refuses the old image).

After it works:

1. Delete the Baileys session: `docker run --rm --network none --user 1000:1000 --volumes-from palui-app-1 alpine:3.24.4 rm -r /data/wa-auth` (the image has no shell or `rm` since it moved to distroless; the nightly backup archives it while it exists). Unlink the old device on the phone if it is still listed. Then the `wa-auth` branch of `scripts/backup.sh` can go in a later PR.
2. Remove `BETTER_AUTH_SECRET`, `RUNTIME_URL` and `CONTROL_PORT` from `.env`; nothing reads them.
3. Keep `palui:prev` (the Node image) until you're sure; deploy.sh replaces it on the next deploy anyway.

Rollback. The Go build adds no migration, so the old image still opens the database. `deploy.sh` rolls back on its own when `compose up` fails, but on the first Go deploy that can't work: it starts `palui:prev` with the new one-service compose file (no runtime, and the healthcheck calls `palui healthcheck`, which the old CLI doesn't have, so it reports "rollback also failed"). To go back to the two-service Node stack, on the Mac mini:

1. `cd ~/selfhost/palui`, then `docker compose stop app && docker compose rm -f app` (the Go server drains on SIGTERM).
2. `docker tag palui:prev palui:latest` (skip if deploy.sh already did; `docker image ls palui` shows the 399 MB image as `latest`).
3. Only if the data looks wrong: restore the newest `/data/backups/pre-deploy-*.db.gz` with the server stopped (gunzip it over `/data/palui.db` and delete `palui.db-wal` and `palui.db-shm`, owned by 1000:1000).
4. Start both services from the last TypeScript commit's compose file, same project and volume: `git show <last TS commit>:compose.yaml > /tmp/compose.ts.yaml`, then `docker compose -f /tmp/compose.ts.yaml --project-directory ~/selfhost/palui up -d --no-build --wait`.
5. Revert the merge on `main` so the next deploy doesn't bring Go back. That deploy builds the Node image again with the old Dockerfile, compose file and pre-deploy script.

After a rollback: sessions the Go server created don't work in Better Auth (sign in again; passkeys enrolled on Go keep working, they are stored in Better Auth's encoding). A WhatsApp pairing done on Go lives in `/data/wa/` and Baileys doesn't read it; the old `wa-auth/` session works only if it wasn't deleted or unlinked.
