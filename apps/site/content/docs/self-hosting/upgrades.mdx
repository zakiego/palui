---
title: Upgrades
description: Deploy a new version with a pre-deploy snapshot and one compose command, and roll back safely if the schema moved.
---

Before you upgrade, read the [Changelog](/docs/changelog) for every release since yours. Anything under "Breaking" tells you what to do first. Your current version is `version` in `GET /health`.

A deploy is three steps. To follow `main`:

```bash
git pull
scripts/pre-deploy.sh
docker compose up -d --build --wait
```

To pin a release instead, check out its tag in place of `git pull`, for example `git fetch --tags && git checkout v0.1.0`.

`scripts/pre-deploy.sh` snapshots the database to `/data/backups/pre-deploy-<UTC>.db.gz` and keeps the newest 3. `--wait` makes Compose wait until the service is healthy, so the command fails if the new version doesn't come up.

The server runs database migrations on start. On a schema it doesn't know (a newer version migrated it) it keeps the runtime off and `/health` fails.

## Nothing is lost during a deploy

The server restarts on every deploy, so the channel sockets drop for a moment. Messages and reminders survive anyway:

- Durable inbox: every inbound message is written to the database before the channel handler returns. Messages that arrive while the server restarts are replayed when it comes back.
- Durable outbox: replies and reminders are rows that stay `pending` until the channel acknowledges them. A row stuck in `sending` for more than 5 minutes goes back to `pending`.
- SIGTERM drain: with `stop_grace_period: 60s`, the server stops taking new turns, finishes the current step and releases its outbox claims before it exits.
- Overdue reminders fire once on start, marked "(telat, harusnya 09.00)" (late, it was due at 09.00).
- Pending approvals are saved, so you can answer one after the restart.

Docs-only changes don't touch the image (the site isn't part of it), so they don't restart the containers.

## Rolling back

Go back to the previous version and run the same command:

```bash
git checkout v0.1.0   # the release you were on, or a commit
docker compose up -d --build --wait
```

A release whose changelog entry says it adds a migration can't be rolled back without the snapshot below.

If the new version had already migrated the database, the old code finds a schema newer than itself. `/health` fails on purpose in that case, so a bad rollback shows as failed instead of half-working. To fix it, restore the pre-deploy snapshot taken just before the upgrade (see [Restore](/docs/self-hosting/backups#restore)), then start the old version again.

<Callout type="info" title="Check the log">
  When a deploy fails, read `docker compose logs app`. A server that finds an unknown schema says so there.
</Callout>
